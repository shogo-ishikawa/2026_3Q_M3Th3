## 機能

### 入力条件

4節の `conditions` という1つの辞書で指定します。

| 項目（キー） | 意味 | 値 |
| --- | --- | --- |
| `"dish_type"` | 料理の種類 | 麺類、ご飯類、スープ、おかず、おまかせ |
| `"main_category"` | 主な食材の区分 | 肉、魚介、野菜・豆類、卵・乳製品、おまかせ |
| `"genre"` | ジャンル | 和食、中華、洋食、エスニック、おまかせ |
| `"meal"` | 食事の場面 | 朝食、昼食、夕食、おまかせ |
| `"servings"` | 人数 | 1以上の整数 |
| `"budget_per_person"` | 1人当たりの材料費の上限（円） | 0より大きい数。制限しないときは `None` |
| `"required_ingredients"` | 必ず使う食材 | 食材名のリスト。すべてを使う料理だけを探す。空のリスト `[]` も可 |
| `"wanted_ingredients"` | できれば使いたい食材 | 食材名のリスト。多く使う料理を上位にする。空のリスト `[]` も可 |

- 「料理の種類」と「主な食材の区分」は別の条件です。レシピには、種類・食材区分・食事の場面をリストのタグで登録しているので、1品が複数の区分に当てはまることもあります（例：フォー風スープ麺は「麺類」と「スープ」）。分類は登録したタグだけで判定し、AIによる推測は基本の検索に使いません。
- 食材名は、空白・空の名前・重複を取り除いてから、単価表の表示名と表記ゆれ辞書（「たまご」「豚肉」「ねぎ」など）で食材IDに直します。
- 単価表にない「必ず使う食材」はエラーとして知らせ、検索しません（黙って除外しません）。単価表にない「できれば使いたい食材」は、順位付けに使えないことを知らせたうえで検索します。
- 「使いたい食材」は、家にあることや費用が0円であることを意味しません。使う材料は、すべて材料費に含めます。
- 不正な入力（選択肢にない分類、0人や 2.5 人、文字列の `"500"` などの予算、リストでない食材指定など）には、直し方が分かる日本語のメッセージを表示します。

### 処理の流れ

1. 入力を確認・整形する（`check_conditions`）。
2. 「おまかせ」以外の分類と、すべての必須食材に合う料理を残す（`unmet_conditions`）。
3. 参考単価から材料費を計算し、予算を超える料理を除く（`calculate_cost`、`suggest_recipes`）。
4. 「できれば使いたい食材」を多く使う順に並べる（`ranking_score`）。同点のときは `RECIPES` に登録した順です。乱数は使わないので、同じ条件なら毎回同じ結果になります。
5. 最大3品を表示する（`show_suggestions`）。条件に合う料理が1品なら1品だけ表示し、条件に合わない料理で3品に埋めることはしません。

候補がないときは「条件に合う料理がありません」と表示し、予算（予算を超えた料理の中で最も安い1人当たりの費用も示します）、分類、必須食材の見直し方を示します。条件は自動で緩めず、候補なしも正常な結果として扱います。

### 出力

候補ごとに、次を表示します。

- 料理名と「登録済みレシピからの提案」であること
- 分類（料理の種類、主な食材、ジャンル、食事の場面）
- 目安の所要時間（人数を変えても同じ値です）
- 指定人数分の材料名・使用量・単位と、材料ごとの概算費用、その根拠になる単価（例：100g当たり160円）
- 合計の費用と1人当たりの費用
- 番号付きの作り方
- 「できれば使いたい食材」のうち、使うものと使わないもの

## 価格と費用計算の前提

- 単価表 `PRICE_TABLE` の価格は、**授業用に決めた仮の参考価格**です。実際の店の価格を調べた値ではなく、実際の価格は地域・店舗・時期で変わります。結果にも、この注意を毎回表示します。
- 単価表は「食材ID、表示名、単位、基準量、その基準量の価格」を持ちます（例：豚こま切れ肉は 100 g 当たり 160 円）。費用は「使用量 ÷ 基準量 × 基準量の価格」で計算します。
- 食材IDごとに単位を1つに決め、レシピの使用量も同じ単位で書きます。単位の変換（大さじ→ml、個→g など）はしません。
- 材料の量は、基準人数から指定人数に比例させて計算します。そのため合計費用は人数に比例し、1人当たりの費用は人数を変えても変わりません。実際には、少しだけ使う調味料やまとめて作る料理などで比例しないこともあり、これは教材のための単純化です。
- 表示する費用は、調味料を含めた「使う量に相当する材料費」の概算です。1袋・1パック単位で買うときの支払額とは異なります。
- 単価が分からない材料（単価表にない食材、または `"price": None`）は0円として扱わず、「費用算出不可」と表示します。予算が指定されているときは、予算内とは判定しません。
- 水（水道水）は費用がごくわずかなので、単価表で0円と明示しています（単価が分からない場合とは区別しています）。
- 予算との比較は丸める前の値で行い、表示だけ1円未満を四捨五入しています。材料ごとの表示を足した値と合計の表示が、1円ほどずれることがあります。入力した予算は、丸めずにそのまま表示します。
- 予算内かどうかは、基本モードと生成AIモードで同じ関数 `is_within_budget`（3-3）を使って判定します。小数の計算には、ごくわずかな誤差が出ることがあります（例：鮭おにぎりを9人分にすると、1人当たり162.6円が `162.60000000000002` 円になる）。予算ちょうどの料理が除かれないように、予算を上回っていても、その差が `math.isclose` で予算の10億分の1（`rel_tol=1e-9`）以内なら予算内として扱います。162.6円の予算なら、許す差は約0.00000016円です。表示用に整数の円へ丸めてから比べる方法は、162.59円の予算に162.6円の料理を入れてしまうような、実際の予算超過まで予算内にするので使っていません。
- 登録した20品の1人当たりの費用は、約31円（中華風卵スープ）から約319円（ガパオ風ライス）です。

## 生成AIモード（任意の追加機能）

ノートブックの6節にある、Gemini API による提案です。**初期状態では無効（`USE_GEMINI = False`）で、APIキーを設定しなくても、ノートブック全体を最後まで実行できます。** 無効のときは、パッケージの導入も APIキーの読み込みもしません。

### 使い方

1. [Google AI Studio](https://aistudio.google.com/apikey) で Gemini API の APIキーを作成します。無料枠の範囲で使う場合、課金の設定は不要です。無料枠の上限（回数など）は AI Studio で確認できます。
2. Colab の左側にある鍵のアイコン（シークレット）を開き、名前 `GEMINI_API_KEY`、値に APIキーを登録して、「ノートブックからのアクセス」をオンにします。
3. 6-1 の設定セルで `USE_GEMINI = True` に変え、6節のセルを上から順に実行します。

- APIキーをノートブックやコードに直接書かないでください。共有や GitHub への登録で漏れるおそれがあります。ノートブックは、キーの値や環境変数を表示しません。
- ローカルで試すときだけ、Colab のシークレットの代わりに、同じ名前の環境変数 `GEMINI_API_KEY` を使えます。
- 無料枠では、送った内容が Google のサービス改善に使われることがあります。個人情報は入力しないでください。

### 使っている SDK とモデル（2026年10月28日に公式ドキュメントで確認）

- SDK：Google の公式 Python SDK `google-genai`（2.3.0以降）。Interactions API（`client.interactions.create`）に、JSON Schema を付けた `response_format` を渡して、構造化された JSON で受け取ります。
- モデル：`gemini-3.8-flash`（安定版で、無料枠があるモデル）。モデル名は 6-1 の `GEMINI_MODEL` だけで変更できます。利用回数の上限にかかりやすいときは、同じく無料枠のある `gemini-3.5-flash-lite` も候補です。
- 1回の実行で送る問い合わせは1回です。SDK の自動再試行は最小に設定しており、利用制限（429）やサーバーの一時的なエラー（5xx）のときに再送されるのは多くても1回です。待ち時間は90秒で打ち切ります。
- 1回だけの問い合わせなので、`store=False` で Google 側に会話を保存しないようにしています。

確認した公式ドキュメント：

- https://ai.google.dev/gemini-api/docs/quickstart （SDK の導入と、`client.interactions.create` の使い方）
- https://ai.google.dev/gemini-api/docs/structured-output （`response_format` による JSON 出力と、使える JSON Schema の範囲）
- https://ai.google.dev/gemini-api/docs/api-key （APIキーの扱い）
- https://ai.google.dev/gemini-api/docs/models （使えるモデルの一覧）
- https://ai.google.dev/gemini-api/docs/pricing （無料枠の有無。無料枠では入力がサービス改善に使われること）
- https://ai.google.dev/gemini-api/docs/interactions-overview （Interactions API、SDK の対応版、`store` の既定値と保存期間）
- https://ai.google.dev/gemini-api/docs/deprecations （モデルの提供終了予定）

モデルや SDK の名前は変わることがあります。動かないときは、上のページで現在のモデル名を確認し、`GEMINI_MODEL` を書き換えてください。

### AIの提案を Python で確かめる内容

- 応答を JSON として読み取れるか、必要な項目（料理名、分類タグ、基準人数、材料、作り方、所要時間）がそろっているか
- 食材IDが単価表にあるか、量が0より大きい数か、同じ食材IDが重なっていないか
- 分類と必須食材が条件に合っているか（基本モードと同じ `unmet_conditions`）
- 予算内か（費用は基本モードと同じ `calculate_cost` で計算し、AIが見積もった金額は使いません）

条件や形式に合わない候補は採用せず、理由を表示します。採用した候補には「生成AIによる提案」と表示します。キーの未設定、利用制限、通信の失敗、SDK を導入できない場合、採用できる候補がない場合などは、理由を短く表示してから「登録済みレシピからの提案」に切り替え、切り替えたことを表示します。6-4 では、手作業で作った確認用サンプル（AIの出力ではないと表示します）を使って、この確認の仕組みを APIキーなしで試せます。

### 制約

- 費用を計算できるように、初版では単価表に登録された食材IDと単位だけを使わせます。登録されていない食材を扱う機能は発展課題です。
- 生成された分量、手順、所要時間は正しいとは限りません。必ず確認してから使ってください。アレルギーへの対応や食の安全を保証する機能ではありません。

## 設計上の判断

- 辞書のキーや食材IDは英小文字の識別子（`"dish_type"`、`"pork"` など）にし、画面の表示や説明は日本語にしました。キーを日本語の名前に対応させる `LABELS` を使い、エラーメッセージには日本語名とキーの両方を出します。
- ジャンルは1品に1つ（文字列）、料理の種類・主な食材の区分・食事の場面は複数可（リスト）にしました。
- 予算の許容誤差は `rel_tol=1e-9` にしました。この教材の計算で実際に出る誤差は、相対値で 10⁻¹⁶ 程度（登録20品 × 1〜50人で最大 2.2×10⁻¹⁶）です。1e-9 はその数百万倍の余裕があり、一方で金額にすると1円よりはるかに小さいので、予算を 0.01円 単位で決めても、本当の超過を見逃しません。
- 並べ方は「できれば使いたい食材の数」だけにし、同点は登録順にしています。前の方に登録した料理が選ばれやすいという偏りが残りますが、改善課題として学生が気付き、直せるようにするためです。
- 「必ず使う食材」と「できれば使いたい食材」の両方に同じ食材があるときは、知らせたうえで「できれば使いたい食材」から外します。
- 生成AIの応答の JSON Schema では、分類にだけ選択肢（enum）を使い、食材IDは選択肢にしていません。公式ドキュメントでは、選択肢の多い enum は複雑すぎるとして拒否される（400）原因になり得るとされているためです。食材IDは指示文で一覧を渡し、Python 側で確かめます。
- 基本モードの関数は、入力の確認・判定・計算（値を返す）と、表示（`print` する）を分けています。生成AIモードは、この判定・計算の関数をそのまま使い、API に固有の処理（SDK の導入、キーの読み込み、問い合わせ）は 6-5 にまとめました。

## 制約と注意

- 価格は仮の値です。実際の価格と比べたものではありません。
- レシピは授業用の簡単な例です。分量と手順は目安で、実際に調理して確かめたものではありません。アレルギーの情報は扱いません。
- 料理は1品ずつ提案します。複数品を組み合わせた献立の最適化は、発展課題です。
- 朝食・昼食・夕食の判定は、登録したタグだけで行います（調理時間などは考えていません）。
- 初版では入力欄やボタンを作らず、ノートブックの変数を編集して条件を指定します。Webアプリ化、Gradio などの画面、データベース、ユーザー登録、Webスクレイピングは発展課題とします。

## 学生が試せる改善例

ノートブックの5節に、改善課題を6件（Pythonの処理を変える課題4件、データの課題1件、AIへの指示の課題1件）載せています。

- 同じ食材で提案が偏る理由を調べ、並べ替え方を変える。
- 朝食向けの判定に、調理時間などの条件を加える。
- レシピや参考単価を追加し、提案できる範囲を広げる。
- 材料費の内訳を見やすく表示する。
- 候補がないとき、どの条件を変えれば見つかるかを示す。
- 生成AIによる提案と、登録済みレシピからの提案を比較する。

## データと出典

- レシピ（料理名、材料、分量、作り方）、単価表、表記ゆれ辞書は、この教材のために作成したものです。特定のレシピサイトの文章や、外部のデータセット・コードは使っていません。
- 生成AIモードは、Google の Gemini API と公式 SDK `google-genai`（Apache License 2.0）を使います。使い方は、上の「確認した公式ドキュメント」に従いました。Gemini API の利用には、Google の利用規約が適用されます。
- 「Open In Colab」のバッジ画像は、Google Colaboratory が公開しているものを参照しています。
