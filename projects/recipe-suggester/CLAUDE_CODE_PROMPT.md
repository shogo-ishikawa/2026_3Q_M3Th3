## 4. 入力できる条件

入力条件は、一か所の辞書にまとめ、項目の意味と変更例を日本語で説明してください。

| 条件 | 選択肢・仕様 |
| --- | --- |
| 料理の種類 | 麺類、ご飯類、スープ、おかず、おまかせ |
| 主な食材の区分 | 肉、魚介、野菜・豆類、卵・乳製品、おまかせ |
| ジャンル | 和食、中華、洋食、エスニック、おまかせ |
| 食事の場面 | 朝食、昼食、夕食、おまかせ |
| 人数 | 1人以上の整数 |
| 予算 | 1人当たりの材料費の上限を円で指定。未指定なら制限なし。指定する場合は正の数 |
| 必ず使う食材 | 食材名のリスト。すべてを使うことを必須条件とする。空リスト可 |
| できれば使いたい食材 | 食材名のリスト。含まれる数を候補の順位付けに使う。空リスト可 |

- 「麺・ご飯・スープ」などと「肉・魚介」などは、別の条件として扱ってください。
- 複数区分に当てはまる料理を登録できるよう、種類や食材区分、食事の場面にはリストのタグを使えます。分類は同梱データで明示し、AIによる推測を基本検索に混ぜないでください。
- 使いたい食材は、家にあることや購入費用ゼロを意味しません。初版では、使う材料はすべて概算材料費に含めます。
- 空白や重複は簡単な前処理で整え、必要なら少数の表記ゆれ辞書を用意してください。未知の必須食材は、黙って除外せず利用者に伝えてください。
- 不正な入力には、学生が直し方を理解できる日本語のメッセージを表示してください。

## 5. 基本モード：同梱レシピからの提案

初期レシピは15〜20品程度を目安とし、複数の種類・食材区分・ジャンル・食事の場面を試せるようにしてください。すべての条件の組合せを網羅する必要はありません。

各レシピには、識別子、料理名、分類タグ、基準人数、材料と分量、調理手順、所要時間を持たせます。材料には、単価表と対応する食材IDを使ってください。教材用の簡潔な例を用意し、特定のレシピサイトの文章を転載しないでください。調理手順と材料一覧に不整合がないか確認してください。

処理は次の順にしてください。

1. 入力を確認・整形する。
2. 「おまかせ」以外の分類指定と、すべての必須食材に合う料理を残す。
3. 参考単価から材料費を計算し、予算を超える料理を除く。
4. 希望食材を多く使う順に並べる。同点の場合の順序も一定にし、初版では乱数を使わない。
5. 最大3品を表示する。1品しかなければ1品とし、条件外の料理を加えて3品に埋めない。

候補がない場合は、「条件に合う料理がありません」と表示し、予算やジャンルなどを見直す案を示してください。条件は自動で緩めず、候補なしは正常な結果として扱ってください。

## 6. 出力と費用計算

候補ごとに、次を読みやすく表示してください。

- 料理名と「登録済みレシピからの提案」であること。
- 指定された人数に対応する、材料名・使用量・単位。
- 番号付きの調理手順。
- 参考の所要時間。人数に合わせて時間を単純に比例させないこと。
- 材料ごとの概算費用、合計費用、1人当たり費用。
- 希望食材のうち、使われるものと使われないもの。

費用は、AIが返した金額ではなく、Pythonで計算してください。

- 単価表には、食材ID、表示名、単位、基準量、その基準量の価格を持たせます。例えば「100 g当たりの参考価格」のように、計算の根拠が分かる形にします。
- 食材IDごとに単位を統一し、材料の使用量と単価表が対応するようにします。初版では複雑な単位変換を導入しません。
- 基準人数から材料の使用量を比例計算します。人数に応じて合計費用が変わり、1人当たり費用は原則変わらないモデルです。この単純化を説明してください。
- 調味料を含めた「使用量相当の材料費」とし、一袋・一パック単位で購入するときの支払額とは区別してください。
- 価格は授業用の仮の参考価格です。実売価格を調査したように書かず、地域・店舗・時期で変わることを表示してください。
- 比較は丸める前の値で行い、円表示の丸め方を統一してください。
- 単価がない材料を0円扱いしないでください。計算できない場合は「費用算出不可」と表示し、予算内であると判定しないでください。

## 7. 任意モード：生成AIによる提案

基本モードを完成させた後に、Gemini APIによる提案を、ノートブック後半の独立した追加機能として実装してください。これはデフォルトで無効にし、キーを設定しなくてもノートブック全体の実行が成功するようにします。

利用は任意ですが、追加機能の実装も今回の成果物に含めてください。

- APIを使うのは、利用者が明示的に有効にした場合だけにしてください。
- 実装時にGoogleの公式ドキュメントを確認し、現行の公式SDKと利用可能なモデルを選んでください。モデル名は一か所で変更できる設定値にし、確認に使った公式URLをREADMEに記載してください。
- API用パッケージの導入とキーの取得は、有効化した経路だけで行ってください。APIキーはColab Secretsの `GEMINI_API_KEY` から読み込みます。ローカルで確認する場合のみ、同名の環境変数を使って構いません。
- キー、環境変数全体、認証情報を含む要求内容を表示しないでください。
- キー未設定、利用制限、通信失敗、SDK未導入などには、短い説明を表示してください。登録済みレシピの基本モードは引き続き使えるようにしてください。
- 自動で大量の再試行をせず、一度の操作で行うAPI呼び出し数を抑えてください。
- APIからは、料理名・分類タグ・基準人数・材料・手順・所要時間を、構造化されたJSONとして受け取ってください。
- 費用計算ができるよう、初版のAIモードは登録済みの食材IDと単位から材料を選ばせてください。この制限を表示し、未知の食材を扱う機能は発展課題にします。
- 形式だけでなく、食材ID、数量、必須食材、指定分類、予算などもPython側で確認してください。未知のID、負の数量、条件違反の候補をそのまま採用しないでください。
- 費用は基本モードと同じ関数で計算し、AIの価格推定値を使わないでください。
- 結果には「生成AIによる提案」と表示します。基本モードへの切替が起きる場合も、切替を明示してください。
- 生成された分量や調理手順は確認が必要であることを説明してください。アレルギー対応や食の安全を保証する機能にはしないでください。
- 実APIを呼べない場合でも、JSONの検証・費用計算はサンプル応答で確認してください。「実API接続は未確認」と報告し、サンプル応答を実際のAI生成結果として表示しないでください。

参考にする公式資料：

- `https://ai.google.dev/gemini-api/docs/quickstart`
- `https://ai.google.dev/gemini-api/docs/structured-output`
- `https://ai.google.dev/gemini-api/docs/api-key`

## 9. 動作確認と完了条件

最低限、次を確認してください。確認は小さな例でよく、大規模なテスト基盤は不要です。

1. APIキーなしの初期状態で、上から実行すると候補が表示される。
2. 種類、食材区分、ジャンル、朝食・昼食・夕食の各指定が、登録データに基づいて反映される。
3. 必須食材はすべて含まれ、希望食材は順位付けに反映される。
4. 人数を1人から2人にすると、材料の使用量と合計費用が2倍になる。
5. 予算内の候補だけが表示され、極端に低い予算や該当しない組合せでは、候補なしと表示される。
6. 食材指定が空でも動き、未知の必須食材や不正な人数・予算には分かるメッセージが出る。
7. AI機能が無効、キーなし、通信失敗の各場合に、基本モードを妨げない。
8. AI応答のサンプルに含まれる未知の食材ID、負の数量、必須条件違反が検出される。
9. 基本モードに外部ファイル、固定されたローカルパス、ネット接続の依存がない。
10. 配布用ノートブックのJSON構造、リンク、出力の消去を確認する。

Colabそのものを操作できない場合は、同等のPython環境でコードセルを先頭から実行して確認してください。ローカルでの実行確認と、Colab実機での確認を区別して記録してください。
