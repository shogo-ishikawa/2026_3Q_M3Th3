## 2. タブとメニュー選択

- 画面は「献立」「記録」「栄養」「メニュー」「買い物」「設定」の順です。通常起動は献立を開き、特定のハッシュを持つ既存リンクはその画面へ進めます。選択中のタブを明示し、キーボードでも切り替えられる状態を維持します。
- 「記録」は主菜を初期表示にして最初に区分を選びます。主菜・副菜は食材カテゴリ→調理法→個別メニューで選び、主食・汁物・飲み物・間食は`family`の種類→`variantLabel`の具体的なメニューへ進みます。「ご飯」と「おにぎり」は別の種類です。
- うどん、そば、焼きそば、パスタ、カレーライス、ピザ、チャーハン、寿司、オムライス、ハンバーガー、飲み物、みそ汁、間食も探しやすく整理します。
- 主菜・副菜は「肉」「魚介」「野菜・いも」「卵」「豆・豆腐」「きのこ」「海藻」などから絞ります。鍋料理と煮込みも調理法として選べます。唐揚げ、フライ・カツ、コロッケ、その他の揚げ物は表示の`fried`（揚げ物）へ統合します。旧ソースの細分類は受け入れ、料理名を失わないようにします。揚げ物、刺身、焼き物、煮物などは調理法として置き、最上位の種類へ戻しません。枝豆、冷奴、ひじき、おから、ポテトサラダ、卵サラダ、春雨、煮物なども副菜の食材と調理法から探せる状態を保ちます。
- 「メニュー」の区分ボタンは「すべて → 主食 → 主菜 → 副菜 → 汁物 → 飲み物 → 間食」の順です。主菜・副菜と「すべて」では食材カテゴリ・調理法、ほかの区分では`family`の種類で絞り込みます。混合料理は補助カテゴリにも入口を持つ場合がありますが、1つのメニューを重複して表示しません。
- 普通の唐揚げは主菜、フライドチキンやポテト、たこ焼きなどはホットスナックです。調理の手軽さだけで主菜を間食へ移しません。
- 既存IDと保存済みスナップショットを保ち、`catalog-metadata.js`の純関数`decorateRecipe`で一覧の分類を補います。料理の表示基準や材料を改める場合も、記録時点の量と栄養を現在のDBから再生成しません。米粉のチヂミを炊飯済みご飯として扱わないなど、料理名と材料の実態を確認してください。
- 旧版で主菜だった麺や丼は内部の`role`を保ち、表示区分は`dishSection`で主食と判断します。`role`を一律に階層の区分へ流用せず、主食が主菜の食材カテゴリへ混ざらないようにします。
- `portion`は基準1人分の表示量です。g・ml・個・皿・杯・枚・袋・貫・切れ・本・食・人分の入力値を`入力値 ÷ portion.amount`で`quantity`へ換算します。
- 材料の生／調理済みの計量状態と、完成品の表示量を混同しないでください。ご飯150gへ生米150gの栄養を当てはめません。

`nature`は調理・提供形態で、食材カテゴリ・調理法・料理の種類・ジャンルとは別です。「焼き物」「刺身」などの調理法と「手作り」「レトルト」などの提供形態を同じ選択肢に混ぜません。`FOOD_NATURES`の`unspecified`（分類未設定）、`home-cooked`（手作り）、`instant`（即席）、`retort`（レトルト）、`fast-food`（ファストフード）、`ready-to-eat`（そのまま）の6値を使います。健康評価を含めません。「そのまま」は調理済み食品などを含み、必要に応じて商品表示どおり温めます。

全収録メニューには形態を明示しています。形態がない旧マイメニューは`recipeNature`で分類未設定とし、手作りと推測しません。「記録」と「メニュー」で種類と形態を組み合わせて探せること、「メニュー」ではジャンルも選べることを維持してください。即席うどんを独立した料理の種類へ分けず、うどんの中で形態を絞り込みます。

### 検索と作り方の表示

- `japanese-search.js`の共通検索をメニュー、記録のメニュー選択、優先・除外食材で使います。NFKC、英字大小、かなを正規化し、漢字や別表記は収録辞書で対応します。空白で分けた語はAND条件です。料理名・小分類名の一致を材料だけの一致より先に表示する順序も保ちます。未知の漢字の読みを推測する機能と説明せず、料理の違いを失う同義語や、隣のフィールドの連結による誤一致を増やしません。表示名と過去の記録を勝手に改名しないでください。
- `cooking-instructions.js`は分類を整えた公開DBに適用し、手作りの下ごしらえ、加熱の進め方、火の通りや仕上げの目安を料理に応じて詳しくします。全品を3工程や固定の工程数にそろえません。材料にない調味料を加えたり、目安時間だけで加熱完了と断定したりしません。
- 組み込みの即席・レトルト・ファストフード・そのままの食品は`steps: []`とし、商品・食品の量と栄養、出典を表示します。調理や再加熱は商品表示へ案内し、利用者が登録した手順や保存済みスナップショットは書き換えません。
- 候補の検査では手作りの手順欠落を引き続き拒否し、作り方が不要な食品の空配列とは区別します。原材料・アレルギー情報の未確認フラグは手順の有無と別に検査します。水や普通牛乳のような既存の単純食品を、手順が空であることだけで候補から失わないようにします。

## 3. カレンダーと摂取量

- 朝食・昼食・夕食・間食の複数品を記録します。状態は`planned`と`eaten`で、摂取量には`eaten`だけを使います。
- カレンダーは自分1人の記録です。メニューの`quantity`は量の倍率、献立設定の`servings`は買い物の人数です。人数を自分の摂取量へ二重に掛けません。
- itemに記録時点の料理名、栄養、材料、基準量、食品群、アレルゲン、確認状況、手順を残します。DBの変更・削除で過去の記録を変えません。
- 任意の`nature`、`sourceNote`、`shoppingKnown`も食事のスナップショットとマイメニューへ引き継ぎます。旧データにない項目を必須にしません。
- 「メニュー」の料理詳細から日付、食事区分、予定／実績、量を指定して記録できます。`record-actions.js`の`createCatalogEntry`で表示量を倍率へ換算し、`describeRecipe`と`itemFromRecipe`から確認フラグと不明値を保持したスナップショットを作ります。未確認商品の記録を、自動提案の許可と混同しません。
- 選択日または日付範囲のリセットは実行前の確認を必須にし、食事・料理・完了日の件数を示します。`previewReset`と`resetEntriesRange`を使い、入力状態を変更しません。予定だけの場合は完了日を保持し、実績を含む場合は範囲内の完了を取り消します。期間に含まれる将来の予定も対象です。直前状態1件だけの取り消しは次のデータ更新や再読み込み後へ持ち越しません。対象外の記録、マイDB、設定、在庫は保持します。
- `completedDays`は「この日の飲食をすべて記録した」と利用者が確認した日です。予定を登録しただけで記録完了にしません。
- 最近の平均は完了日のうち成分が分かる日を使い、栄養素ごとの対象日数を表示します。入力途中や未記録の日を0として分母へ加えません。

## 4. 栄養と比較の目安

対象は`kcal`、`protein`、`fat`、`carbs`、`fiber`、`salt`の6成分です。エネルギーはkcal、それ以外はgです。材料の`nutritionPerUnit`は宣言された1g・1ml・1個など当たりで、100g値とは区別します。

不明値は`null`です。0へ置き換えず、既知の合計と不明分の存在を分けて表示します。食品の対応、密度、調理状態を変えたら出典も更新します。市販品の固有値を捏造せず、代表的な成分表食品と製品差を明記してください。

`prepared-foods.js`の市販食品35品は特定商品や店舗を保証するDBではありません。成分表の対応食品と、明示した参考配合による概算を区別し、前提を`sourceNote`に残します。カップ麺は乾燥製品と添付調味料の量を基準にし、スープを残した割合や湯切りによる栄養の流出を自動で補正しません。レトルトのカレーや丼ものはご飯180gを含む完成1食として登録しているため、ご飯を別に加えて二重計上しません。

プロフィールには年代、基準表の性別区分、活動量、比較方法を持ちます。初期値は未選択・手動です。明示された一般成人の組み合わせにだけ2025年版食事摂取基準を使います。75歳以上の活動量「高い」など未対応の値を補間しません。

エネルギーは参照体位の推定値、たんぱく質は推奨量、脂質・炭水化物は比率の範囲です。範囲の中央から換算した値を公式の推奨量と説明しません。食物繊維の「以上」と食塩相当量の「未満」を区別します。

手動の比較値も残してください。妊娠・授乳中、18歳未満、体格による個別調整、治療用の自動計算は未対応です。1日や少数の不完全な記録から、健康状態や栄養不足を診断する表現を使いません。

## 5. 献立と除外条件

- 朝・昼・夕の3食をまとめる`meal: all`と、朝食・昼食・夕食・間食の単独指定を使えます。1〜7日分、買い物用に1〜8人分です。allの結果も各記録には実際の食事区分を保存します。候補不足なら全体を未作成にし、途中の提案を予定として保存しません。
- 主食はおまかせ・固定・別の主食なしから選び、生成後は`updatePlanStaple`で1食だけ種類と量を変えられます。`stapleMode`は`adaptive`・`fixed`、`stapleId`は`auto`・`none`・具体IDを使います。麺や丼へ別の主食を重ねず、変更時も除外条件を再検査します。量の変更は栄養・予定・買い物に同じ倍率で反映します。
- 主食と飲み物を種類・小分類・量で指定します。量は提案の栄養、`day.quantities`、予定のsnapshot、買い物へ同じ倍率で引き継ぎます。
- パスタやカレーライスなど一品で主食を含む料理は、別の主菜やご飯を重ねない構成にします。
- ジャンルの単一指定・比率、気分、優先食材、料理の変更、一時的な不採用を維持します。
- アレルギーと個別食材の除外を優先し、原料の`derivedFrom`と祖先のアレルゲンを確認します。候補が足りなくても条件を黙って外しません。
- `prepared-foods.js`の市販食品35品は`allergensKnown: false`、`ingredientsKnown: false`で、自動提案の対象外です。固定した主食、飲み物、間食、差し替えでも未確認の候補を戻しません。閲覧や食べた事実の記録はできます。
- `recipeConfirmation`はマイメニューと即席・レトルト・ファストフードについて、確認フラグの欠落も未確認と扱います。「そのまま」の市販サンドイッチなどには明示的な未確認フラグがあります。参考アレルゲン一覧や購入商品があるだけで確認済みとしません。
- 食品群と主なたんぱく源は直接材料だけから求めます。しょうゆの原料が大豆であることだけで大豆料理を1食食べたと数えません。
- 予定や対象の食事より後の記録を摂取量へ加えません。最近の栄養は記録完了日から比較し、不明な成分を0として優遇しません。
- お酒は記録専用とし、family `alcohol`を献立・固定飲み物・差し替えへ入れません。
- ソイ／ホエイ、水割り／牛乳割り、清涼飲料水、補食・栄養補助食品を区別します。商品の公式栄養表示を`manualNutrition`へ使う場合も、原材料全体とアレルギー情報は未確認のまま保ち、自動提案には使いません。範囲表示や不明値を平均や0で埋めず、粉gから完成mlを推定しません。
- 厳密に目標値を満たす最適化や健康診断を実装済みと説明しません。

## 6. 手入力と自分のDB

未登録の食事は名前と量だけでも記録でき、栄養・材料・作り方は任意です。自分のDBへ保存するかは利用者が選びます。roleは`main`、`side`、`soup`、`staple`、`drink`、`snack`です。

`allergensKnown`と`ingredientsKnown`は初期値`false`です。空の配列を確認済みと読み替えません。アレルギー未確認の自作メニューは自動提案せず、材料全体が未確認で追加除外がある場合も候補から外します。食べた事実として残すことは妨げません。

調理・提供形態と`sourceNote`（栄養や商品のメモ）は任意です。`shoppingKnown`は買い物に必要な商品の種類と分量がそろったという別の確認で、原材料やアレルギーを確認した意味ではありません。これらを編集・保存・再読み込みしても元の意味を保ってください。商品表示を確認したマイメニューを候補にする場合も、登録された材料と祖先のアレルゲンの検査を通します。

全材料を確認した場合に「材料から栄養の概算を入力する」を押すと入力欄を更新します。商品の表示値は後から直せます。保存時に空欄を勝手に計算しません。

自分のDBから料理を削除しても過去の記録を保ち、選択中の主食・飲み物が削除された場合は設定を戻します。

## 7. 買い物と在庫

提案中の献立かカレンダーの予定を対象に、材料へ量の倍率と買い物用の人数を掛けます。同じ食材をすべて合計してから、手持ちの量を一度だけ差し引き、負の購入量を作りません。

材料の未登録・全体未確認・現在のDBにない材料があれば名前を知らせます。空の材料一覧を買い物不要と誤表示しません。

`ingredientsKnown: false`でも`shoppingKnown: true`で購入商品と量が登録済みなら、その分は合算できます。バーガーは完成品1個として数え、参考配合の材料へ展開しません。レトルトの完成1食では購入する具とご飯を集計します。原材料が未確認の料理として注意にも残してください。`shoppingKnown: true`なのに商品一覧が空のJSONは拒否します。買い物を集計できることを、自動提案に使えるという意味へ読み替えません。

在庫は材料の登録単位で数量を持ちます。数量だけの更新では提案を維持して再集計します。購入済みチェックと在庫を区別し、消費の自動記録、パック単位への丸め、価格計算を実装済みと説明しません。

## 8. 保存と個人情報

保存キーは`kondate-note-v3`、形式は`version: 3`です。個人の食事、プロフィール、DB、設定をGitHubや共通DBへ送る機能を追加しません。ログインやAPIキーなしで使える状態を維持します。

アプリと公開DBの版は3.4.0ですが、保存形式を4へ上げません。`settings.meal`にallを認め、`stapleMode`は任意で検査します。項目がない旧JSONも受け入れ、以前の主食指定を引き継ぎます。階層も表示時に求め、保存データへ必須項目を増やしません。既存IDと過去のスナップショットを維持します。`nature`、`sourceNote`、`shoppingKnown`は任意の追加項目で、これらがない旧v3のJSONを引き続き読み込みます。`nature`は登録された6値、`sourceNote`は最大2000文字の文字列、確認状況は真偽値として検査します。過去の栄養値や確認状況を現在のDBから再生成しません。

v1・v2の保存とJSONから、アレルギー、除外条件、好み、記録を引き継ぎます。旧版にないプロフィールを推測せず、完了日も自動で付けません。読み込み時に旧保存領域や不正なデータを削除しません。

JSONの型、許可した項目、日付、ID、数量、栄養、件数、サイズ、危険なプロパティを検査します。不正な入力で現在の状態を一部だけ変えず、料理名やメモをHTMLとして挿入しません。食事の一括削除では対象を明示し、DBや設定まで黙って消しません。

## 9. 教材と公開物
