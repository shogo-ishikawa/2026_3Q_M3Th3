## 3. 維持する機能とデータの約束

### カレンダーと食事の量

- 月表示で日付を選び、朝食・昼食・夕食・間食を記録できます。同じ食事に複数の料理を登録できます。
- 状態は`planned`と`eaten`です。摂取量に使うのは`eaten`だけで、未来の予定や未記録の食事を食べた量として扱いません。
- カレンダーの栄養と材料は1人分が基準です。各itemの`quantity`は食べた量の倍率です。
- 献立設定の`servings`は買い物用の人数です。これを摂取量へ二重に掛けないでください。
- itemには料理名、栄養、材料、食品群、アレルゲン、確認状況、作り方を記録時点の内容として保存します。元のDBを変更・削除しても過去の記録を保ちます。

### 献立と除外条件

- 1〜7日分、買い物用に1〜8人分を指定できます。朝食・昼食・夕食・間食の区分を維持します。
- 主食はおまかせ、追加なし、具体的な主食の指定に対応します。主食を含む主菜にご飯などを重ねないでください。飲み物の指定にも対応します。
- ジャンルの単一指定と比率、気分、優先食材、組み合わせの変更、一時的な料理の除外を維持します。
- アレルギーと個別食材の除外は優先する条件です。原料の`derivedFrom`と先祖のアレルゲンも確認し、候補不足でも黙って条件を緩めないでください。
- 同じ日の提案する食事より前の食事と過去の食べた記録から、料理や主な食材の重複を減らします。分かる栄養と手持ち食材も順位付けに使います。
- 比較値を満たす厳密な最適化や、個人の健康状態を判定する仕組みとは説明しないでください。

### 手入力と自分のDB

- 未登録の食事は料理名、量、栄養、材料、作り方を手入力できます。自分のDBへ保存するかは利用者が選びます。
- roleは`main`、`side`、`soup`、`staple`、`drink`、`snack`です。マイレシピの材料は1人分として保存します。
- `allergensKnown`と`ingredientsKnown`の初期値は`false`です。空の配列を「確認済みで該当なし」と読み替えないでください。
- アレルギー情報が未確認のマイレシピは自動提案しません。材料全体が未確認で食材の除外条件がある場合も除きます。
- 「材料から栄養の概算を入力する」を明示的に押した場合だけ、全材料を登録した確認を条件に概算を入力します。ボタンは入力欄を更新するため、商品の表示値などはその後で直せるようにします。押さない場合の空欄は不明のまま残します。
- マイDBの削除では過去の記録を消さず、削除したメニューが選択中の主食や飲み物なら設定を戻します。

### 栄養と不明値

- 対象は`kcal`、`protein`、`fat`、`carbs`、`fiber`、`salt`の6項目です。単位はエネルギーのみkcal、ほかはgです。
- 食材の`nutritionPerUnit`は宣言された1g、1ml、1個など当たりです。100gの値と混同しないでください。
- 不明値は`null`です。0に置き換えず、分かる分の合計と不明分の存在を表示します。
- 栄養の根拠は`docs/nutrition-sources.md`を参照します。食品の対応や換算を変えたら出典も更新してください。
- 比較値は編集可能な学習用の参考値です。初期値を個人への推奨量と説明しないでください。

### 手持ちの食材と買い物

- 手持ちの食材は材料IDと数量で保存します。同じ食材の登録は数量の更新です。単位は材料の登録単位に統一します。在庫の数量更新は提案中の献立を消さず、買い物を再集計します。
- 提案中の献立かカレンダーの予定を対象に必要量をまとめ、数量倍率と買い物用の人数を掛けます。
- 在庫を食材ごとに一度だけ差し引き、買う量は0を下回らないようにします。食べた記録は買い物の対象にしません。
- 材料の情報が不十分なメニューは名前とともに知らせます。材料0件を「買い物不要」と誤表示しないでください。
- 購入済みのチェックと数量在庫を区別します。在庫の自動消費や購入単位への丸め、支払額の計算を実装済みとは説明しないでください。

## 4. 保存と個人情報

記録は`kondate-note-v2`としてブラウザー内に保存します。個人の食事記録、マイDB、除外条件をGitHubや共通DBへ送る機能は追加しないでください。アカウントやAPIキーなしで基本機能が動く状態を維持します。

JSONによるバックアップと読み込みを維持します。型、日付、識別子、数量、栄養、件数、ファイルサイズ、許可した項目だけかを検査してください。危険なプロパティや重複ID、組み込みレシピと衝突するマイレシピは拒否します。不正な入力で現在の状態を一部だけ書き換えないでください。

旧`kondate-note-v1`と旧JSONを読み込む際はアレルギー、除外食材、好み、記録を引き継ぎます。メモだけの料理は未知の栄養として残し、読み込み時に旧保存データを削除しません。読み込めない保存データも自動で消さず、利用者へ知らせます。

食事の記録の一括削除はカレンダーだけが対象です。DBや設定まで削除する操作を追加する場合は、利用者が範囲を理解できる表示にしてください。

## 6. 確認と報告

変更に合うテストとブラウザー確認を行い、次の境界を確認してください。

1. 朝昼夕間食の登録、予定と食べた記録の切り替え、複数品、量の変更。
2. 1人分の栄養と人数分の買い物が混ざらず、不明値が0にならないこと。
3. アレルギー、先祖原料、主食・飲み物の指定が変更操作でも守られること。
4. 手入力と任意のDB保存、未確認情報の除外、DB削除後も過去の記録が残ること。
5. 複数日の必要量から在庫を1回だけ差し引き、材料不明の料理を知らせること。
6. 旧保存と旧JSONからの移行、不正JSONの拒否、保存できない環境の案内。
7. スマートフォン幅、キーボード操作、レシピ表示、コピー、バックアップ。

実際に確認した範囲を`docs/validation.md`へ記録し、未確認の環境と区別してください。README、使い方、出典、配布リンクを実装とそろえます。最後に変更内容、確認結果、残る制約、学生が最初に変更するとよい箇所を簡潔に報告してください。
