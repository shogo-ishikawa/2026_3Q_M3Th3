# 設計と開発

## この版で扱うこと

「献立ノート」は、登録したレシピから食材の除外条件を守って候補を探し、食事の記録を使って料理の繰り返しを減らすアプリです。Web版はJavaScriptだけで動き、外部APIやPython実行環境を利用者に準備してもらう必要はありません。

Pythonの学習には`meal_planner.ipynb`を使います。ブラウザの画面と保存処理はJavaScriptにまとめ、Colabではリスト・辞書・条件分岐・繰り返し・関数を使う部分を読みやすく扱います。従来の`recipe_suggester.ipynb`は、参考価格を含む初期教材として保持しています。

## データと候補の関係

| データ | 主な情報 |
| --- | --- |
| アレルゲン一覧 | 識別子、表示名、表示義務・推奨の区分 |
| 食材辞書 | 食材名、分量の単位、含むアレルゲン、食品群、派生元の食材ID（derivedFrom）、必要に応じた製品確認の注記 |
| レシピ | 主菜などの区分、基準人数、材料の識別子と量、作り方、調理時間 |
| 食事の記録 | 日付、食事の場面、レシピまたは手入力の食品群、主なたんぱく源、メモ |
| 提案の希望 | ジャンルの選び方・割合、気分、優先食材など |

レシピのアレルゲンは、材料として使う食材の情報から求めます。料理名の部分一致だけで判定したり、料理ごとに重複したアレルゲン一覧を手入力したりしない構成です。調味料も材料に含めます。

食材の情報が欠けている場合は、アレルゲンを含まないものとして扱いません。データを直してから候補として使えるようにします。

`derivedFrom`には確認できる原料の食材IDを登録します。例えばトマト缶からトマトへたどることで、トマトの除外を缶にも適用します。アレルゲンも派生元と合流しますが、食品群は実際に使う材料だけから求めます。未知の参照や循環は候補外にします。

## 除外条件を優先する

献立作成と差し替えは、同じ候補の絞り込みを通します。

1. レシピと材料の情報を確認する。
2. 指定したアレルゲン・個別食材を含む料理を除く。
3. 残った候補から、履歴や料理の組み合わせを使って選ぶ。

履歴の偏りを減らすために、除外した食材を戻すことはありません。主菜・副菜・汁物などをそろえられない場合は、候補が足りない区分を返します。好みや見栄えのために、条件外の料理で埋め合わせる処理は入れません。

## ジャンルと気分を反映する

ジャンルは、おまかせ・1種類の指定・割合の指定を使い分けます。和食・洋食・中華・エスニックに加え、それらに当てはめにくい料理はその他として残しています。

割合指定は主菜を対象にします。各割合に日数を掛けた値の整数部分を先に割り当て、残った日数を小数部分の大きいジャンルから配ります。小数部分が同じ場合は、登録したジャンルの順で割り当てます。指定値と作成結果を分けて表示し、日数が少ない場合の丸めも確認できるようにします。「今回は除外」にした主菜は、実績の件数から外します。

希望するジャンルに候補がない場合は、0%のジャンルも含め、除外条件に合う別のジャンルから提案し、その変更を表示します。ジャンルや気分は希望、アレルギーと個別食材の除外は優先して守る条件として扱います。

気分は、指定なし・さっぱり・ガッツリ・時短・定番です。料理に付けたタグや優先食材を使って候補を順位付けします。エネルギー量や個人の必要量から分類する仕組みではありません。

## 作る料理と買い物の対象

生成後の料理には、日付と料理を組にした一時的な不採用を設定できます。「今回は除外」とした料理は買い物リストと食事の記録から外し、「戻す」で復元します。レシピIDを今後ずっと禁止する設定にはしません。

買い物リストでは、家にある材料をチェックして購入対象から外せます。非表示とコピーにも同じ選択を反映します。一時的な不採用と手持ち食材のチェックは、献立を新しく作るとリセットします。

## 履歴を使う提案

食品群は、主食・副菜・主菜・牛乳／乳製品・果物という区分を参考にしています。ただし、このアプリは材料から分かるグループの有無を数える簡易的な仕組みです。公式の食事バランスガイドで使う「つ（SV）」や、必要な摂取量は計算しません。

各提案日から見て過去7日間と、提案する食事より前の当日の記録を使います。同じ日付・食事の場面の重複記録は1食にまとめます。メモだけで食品群が分からない記録からは、食事の偏りを推定しません。

同じ料理や主なたんぱく源が続くことを減らすよう候補を選びます。記録されていない朝食・昼食などは推定しません。自由記入の文章をAIで解析する機能も使いません。

記録で登場回数が少ない食品群を含む料理へ軽く加点し、同じ献立ですでにそろった群への重複加点を避けます。主食は献立の構成でそろえます。複数日分では先に選んだ日の献立も重複を避ける参考にしますが、未食の予定と食べた記録は区別します。

人数は材料の量と買い物リストに反映します。年齢・体格・活動量などに応じた栄養計算は行いません。食事指導を受けている場合は、その指導に合わせて使ってください。

## 保存の範囲

設定と食事の記録は`localStorage`に保存します。サーバーへの送信や端末間の自動同期は行いません。JSONの読み込みでは、形式、日付、食事の場面、識別子などを確かめます。不正な内容を受け入れて現在の記録を書き換えることを避けます。

以前の保存データに提案の希望がない場合は初期値を補い、既存の食材制約と履歴を保持します。作成途中の献立、日ごとの一時的な不採用、家にある材料のチェックは保存しません。

保存機能を変更するときは、古い形式のデータを読み込んだ場合の挙動も決めてください。外部から読み込むメモや料理名をHTMLとして挿入せず、文字列として表示することも大切です。

## ローカルで開く

配布ZIPを展開してできた`v1.1.0/`を、例えば次の場所に置きます。

```text
/Users/shogo/Dropbox/share_data/open_material/misc/apps/MealPlanner/v1.1.0
```

ターミナルでそのフォルダーへ移動し、実行します。

```bash
python3 tools/serve.py
```

表示されたURLをブラウザで開いてください。終了はControl+Cです。

## 変更を確認する

Web版のテストを実行します。Node.jsが必要です。

```bash
npm test
```

データを追加したときは、材料の識別子、単位、アレルゲン情報、手順がそろっているか確認します。同じ料理を少し改名したものだけで品数を増やさず、材料や作り方の違いが分かる料理を追加してください。

| 変更 | 比べること |
| --- | --- |
| レシピの追加 | 除外条件に正しく反応し、材料と手順が一致するか |
| 調味料の追加 | 市販品の原材料にばらつきがあることを注記し、既知のアレルゲンを落としていないか |
| 履歴の採点方法 | 同じ入力で提案がどう変わるか。除外条件を守っているか |
| ジャンル比率 | 合計100%、整数件数への配分、候補不足時の表示、除外条件の維持 |
| 一時的な不採用 | 対象の日だけ買い物と食事の記録から外れ、復元できるか |
| 表示や保存の変更 | 条件の変更後に古い献立を使わないか。再読み込みや不正なJSONで記録が壊れないか |

WebのデータやPythonの例を変えた場合は、同じデータを埋め込んだNotebookを作り直して確認します。生成にはNode.jsも必要です。

```bash
python3 tools/build_notebook.py
python3 -m unittest discover -s tests -p 'test_*.py' -v
python3 tools/build_release.py
```

最後のコマンドで配布用ZIPを作成します。展開後のフォルダー名はバージョン番号になります。

## HTTPSで授業リポジトリへ同期する

作品のフォルダーとは別に、授業リポジトリ全体を置く場所を指定します。

```bash
cd /Users/shogo/Dropbox/share_data/open_material/misc/apps/MealPlanner/v1.1.0
bash tools/sync_project.sh /Users/shogo/Dropbox/share_data/open_material/misc/apps/2026_3Q_M3Th3
```

同期スクリプトは授業リポジトリの`projects/recipe-suggester/`を更新します。実行前に変更内容を確認し、食事の個人記録や除外条件を書き込んだファイルを配布物へ混ぜないでください。

このスクリプトはmainを取得し、公開用ファイルをコピーしてコミット・pushまで行います。未コミットの変更があるリポジトリでは停止します。

作品はリポジトリ共通のGitHub Actionsで公開します。ほかの作品の公開先を切り替える必要はありません。
