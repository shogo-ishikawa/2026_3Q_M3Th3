# 設計と開発

対応版：Meal Palette v3.7.0 ／ 更新日：2026年11月13日

## 機能を6つの画面に分ける

Meal Paletteは献立づくりから食事の記録、栄養の振り返り、買い物へ進めるアプリです。v3.7.0は855品のレシピと372種類の食材・調味料を収録しています。肉じゃがとお好み焼きでは具材を選んで材料・栄養・手順を更新します。ほかの料理もバリエーションを同じ入口へまとめ、一覧を選びやすくしました。既存のサラダの材料選択、カレンダー、3食まとめての提案、食事ごとの主食調整、範囲リセット、寿司の単位別入力も維持します。

タブは「献立 → 記録 → 栄養 → メニュー → 買い物 → 設定」の順です。特定のハッシュを持たないURLでは献立から始め、既存の記録やメニューへのリンクは引き続き対応する画面を開きます。選択状態、フォーカス、矢印キーによる操作を保ちます。

ブラウザー内のJavaScriptで動きます。個人の食事やプロフィールを送信するサーバー、ログイン、外部APIキーは使いません。Pythonの学習は`meal_planner.ipynb`へ分け、リスト・辞書・条件分岐・繰り返し・関数による候補選びを扱います。`recipe_suggester.ipynb`は参考価格を使う初期教材です。

## 料理の種類と量を分ける

主食・汁物・飲み物・間食の種類は`family`、小分類の表示名は`variantLabel`で扱います。主菜・副菜の食材カテゴリと調理法は`dish-hierarchy.js`で別に定義します。`data.js`で全メニューを統合した後、純関数`decorateRecipe`を使って分類情報を整えます。既存のレシピIDを保ち、保存済みの食事の数値を書き換えません。v3.3.0の寿司は新たに選ぶ基準量を見直しますが、過去のスナップショットを現在のDBから再生成しません。

「ご飯」と「おにぎり」は別の大分類です。うどん、そば、パスタなどの料理の違いや、みそ汁の具の違いは各大分類の中へまとめます。寿司、オムライス、ハンバーガーにも独立した分類があります。旧版で主菜として登録された麺や丼は内部の`role`を保持する場合もありますが、一覧では`family`に対応する主食の種類から探せます。

主菜・副菜の画面では「食材カテゴリ → 調理法 → 個別メニュー」の順に選びます。肉や魚介、野菜・いも、卵などから食材を選び、揚げ物・刺身・焼き物・煮物・和え物などで絞ります。唐揚げや刺身を最上位の種類として並べる構成にはしません。唐揚げ、フライ・カツ、コロッケ、その他の揚げ物は表示上の`fried`へまとめます。旧ソースの細分類は検索や検査で受け入れ、料理名も保ちます。ご飯とおにぎりを分ける主食の分類や、汁物・飲み物・間食の種類は保ちます。

既存の`family`は互換性を保ちながら、内部の種類や量の換算に使います。v3.6.0では単品の納豆、おろし納豆、ゆで卵の3品を`role: side`・`family: small-dish`へ整理します。材料・量・栄養・手順は変えず、保存済みの主菜という記録も書き換えません。旧版の麺や丼に`role: main`が残っていても、表示区分は`dishSection`で主食として扱います。枝豆は副菜、オーブン唐揚げは主菜というv3.1.0の整理も維持します。米粉のチヂミをご飯として扱ったり、米粉の重量から炊飯済みご飯の量を推定したりしません。

### 菓子・スイーツの種類

間食の`family`にチョコレート、飴・キャラメル・ラムネ、グミ、クッキー・ビスケット、スナック菓子、せんべい・米菓、ドーナツ、ケーキ、和菓子、アイス・氷菓の10種類を設けます。その他の菓子・スイーツ、チーズ、ホットスナック、果物、ナッツ、ヨーグルト、補食も別に保持します。過去の記録の`family`や名前は変更せず、現在の公開DBへ分類を付けます。ポッキーなど食品そのもののブランド名と、店舗名を冠した料理の見出しは区別します。

### 主菜・副菜の表示階層

`dish-hierarchy.js`は保存済みの料理や材料を書き換えない表示用のモジュールです。`dishClassification`は`section`、主となる`category`、複数の入口を持つ場合の`secondaryCategories`、`method`を返します。食材カテゴリや調理法は探すための情報であり、アレルゲンや栄養を推測する根拠には使いません。既存メニューはIDごとに確認した対応表を使います。追加メニューはソースコードに`displayCategory`・`displayMethod`・`displaySecondaryCategories`を明示し、こちらを優先して読みます。登録されたカテゴリ・調理法と補助カテゴリの整合性も検査します。未分類のマイメニューは「その他」とし、材料名から主材料や調理法を推測して埋めません。

v3.2.0で追加した87品は主菜・主食50品、副菜・汁物37品です。煮魚やムニエル、シチュー、鍋料理、丼、ドリア、基本のサラダや温野菜などを補いました。煮込みと鍋料理も独立した調理法で探せます。調査は[メニューの調査と分類](menu-research.md)にまとめ、店舗商品の配合や栄養を再現するものとは区別しています。

| API | 役割 |
| --- | --- |
| `FOOD_CATEGORIES`・`COOKING_METHODS` | 食材カテゴリと調理法の表示名・選択順 |
| `dishSection`・`dishClassification` | 料理の表示区分と階層情報 |
| `browseDishes` | 区分、食材カテゴリ、調理法、検索語、調理・提供形態による絞り込み |
| `availableDishCategories`・`availableCookingMethods` | 同じ条件で使える選択肢と件数 |

検索と選択肢の共通条件は`{section, category, method, query, nature}`です。複数の食材を使う料理は主カテゴリと補助カテゴリから探せる場合もありますが、同じ料理を一覧へ重複させません。食材カテゴリや調理法を指定した検索と件数は主菜・副菜を対象とし、主食などを仮の「その他」へ混ぜません。

「記録」は主菜を初期表示にして最初に区分を選び、主菜・副菜では食材カテゴリと調理法、ほかの区分では従来の種類からメニューへ進みます。「メニュー」の区分ボタンはすべて・主食・主菜・副菜・汁物・飲み物・間食の順です。主菜・副菜と「すべて」では食材カテゴリ・調理法を使い、主食・汁物・飲み物・間食では`family`を使います。

`portion`は基準の1人分を画面に表示する量です。`amount`と`unit`を持ち、例えばご飯150g、おにぎり1個、飲み物200mlのように定義します。寿司の「貫」「切れ」と、市販食品の「食」「本」も扱えます。握りと軍艦は1貫、細巻と太巻は切り分けた1切れ、盛り合わせは1皿を基準にします。巻物は1本の材料を切れ数で割って1切れの栄養と材料へ換算します。入力した量は`入力量 ÷ 基準量`で内部の`quantity`倍率へ換算します。

完成した料理の量と材料の計量状態は別です。ご飯を150g食べたという記録に、生米150gの栄養を使うことはありません。生米を使って炊くレシピでは材料を生の重量、表示する1人分を炊飯後の量として定義します。

### 単品食品とサラダの組み合わせ

`accompaniment-foods.js`はツナの油漬けと水煮、生卵、温泉卵、味付けのり、たらこ、明太子、鮭フレークを副菜の単品として扱います。ご飯や別添え調味料を材料へ暗黙に足さず、個数やg数を独立して記録します。生と加熱済みの食品を区別し、商品表示の値を使うものは参照商品と規格を残します。成分表の値が分かることだけで、製品の原材料全体を確認済みにしません。

サラダはすべての組み合わせを共通DBへ列挙せず、`salad-builder.js`で選んだ材料と量から1人分のマイレシピを作ります。`SALAD_COMPONENTS`は野菜と計量状態、`SALAD_DRESSINGS`は家庭用ドレッシングの配合と基準量です。`buildSaladRecipe(config, data)`が材料の量を合算し、`recipeNutrition`と同じ6成分の不明値ルールで栄養を計算します。選択していない材料やドレッシングを栄養・アレルゲン・買い物へ残しません。ゆでたブロッコリーには生の成分値を使いません。

選択結果はカレンダーへ保存する時点で独立したスナップショットにします。マイメニューにも保存するかは利用者が選び、既存の保存形式3で保持します。野菜の量やドレッシングを後から変えても過去の記録を再計算しません。買い物はスナップショットの材料に量と人数を掛け、在庫を一度だけ引く既存処理を使います。入力が空、材料が重複、量が不正などの場合は登録せず、記録やDBを一部だけ更新しません。

UIは「生野菜サラダ（ドレッシングなし）」の詳細内で材料とg数、ドレッシングとg数を選びます。「記録」で対象メニューを選んだ場合も「材料を選んで記録」から同じ画面へ進みます。日付や食事区分の入力は既存のカレンダー追加欄を使い、「この組み合わせをマイメニューにも保存」でDBへの保存を選びます。選択肢と計量の詳細は[サラダの組み合わせ](salad-builder.md)、単品食品の基準と出典は[ご飯のお供の出典](accompaniment-sources.md)へまとめています。

### 料理の中で具材やバリエーションを選ぶ

肉じゃがとお好み焼きの選択は、既存のレシピを変更せずに1皿分のマイレシピを生成します。肉じゃがは牛肉と豚肉を切り替え、お好み焼きは代表的な配合から具材とg数、ソースやマヨネーズの量を調整します。栄養とアレルゲン、材料、調理手順は確定した配合から求めます。肉や海鮮、麺の有無に合わせて必要な工程も変えます。配合は[料理の具材選択](dish-customisation.md)にまとめています。

一覧は共通DBのレシピ数と表示項目数を区別します。既存855品はIDも内容も維持し、うどん、そば、パスタ、みそ汁、オムレツなどは表示時に料理ごとの入口へまとめます。グループの中では選択中のレシピIDを使い、材料・栄養・手順・基準量を切り替えます。手作りと購入品、主食を含む料理と添え物、区分や提供形態が異なる料理を安易に同一化しません。一覧では検索や区分などで絞った候補だけをまとめます。詳細でほかの種類を選ぶ際は検索語だけを外す場合もありますが、アレルギーや食材除外、区分や形態などの条件は保ちます。まとめる処理で除外した候補を戻しません。対象と採否は[バリエーションの整理](menu-variations.md)を参照してください。

具材の組み合わせ全てを共通DBへ追加しません。食事へ確定した1品のスナップショットを記録し、利用者が選んだ場合だけマイメニューも保存します。保存形式はv3のままで、新しい必須項目を加えません。配合の変更やマイメニューの削除で過去の材料・栄養・手順を再計算しません。

## 料理の種類と調理・提供形態を組み合わせる

`nature`は`family`、食材カテゴリ、調理法とは別の分類です。「焼き物」「煮物」「刺身」などが調理法、「手作り」「レトルト」などが調理・提供形態です。例えば手作りのうどんもカップうどんも`family: 'udon'`にまとめ、調理・提供形態で絞り込みます。健康への良し悪しや栄養バランスの評価は表しません。

| 値 | 表示 | 扱い |
| --- | --- | --- |
| `unspecified` | 分類未設定 | 利用者が形態を指定していない手入力メニュー |
| `home-cooked` | 手作り | 材料を組み合わせて調理・準備する料理 |
| `instant` | 即席 | カップ麺、袋入り即席麺など |
| `retort` | レトルト | レトルトのカレーや丼ものなど |
| `fast-food` | ファストフード | 店舗や銘柄を特定しないバーガーの一般例など |
| `ready-to-eat` | そのまま | 果物、飲料、完成品など。必要に応じて表示どおり温めます |

全収録メニューに形態を明示し、手作り、そのまま、即席、レトルト、ファストフードに整理しています。形態がない旧マイメニューは`recipeNature`で「分類未設定」と表示し、勝手に手作りと断定しません。「記録」と「メニュー」では料理の種類と形態を組み合わせて探せます。「メニュー」には和食・洋食・中華などのジャンル指定もあります。

レトルトのカレーや丼ものは、ご飯を含む完成1食で登録しています。例えばレトルトの具200gとご飯180gを合わせて1皿です。ご飯を別に加えると二重計上になります。カップ麺は乾燥製品と添付調味料の量を基準にし、調理用の湯やスープを飲み残す割合から栄養を自動補正しません。製品固有の実測値と参考配合の概算は`sourceNote`で区別します。

## カレンダーは1人分を保存する

保存形式は`version: 3`です。

| データ | 内容 |
| --- | --- |
| `entries` | 日付、食事区分、予定／食べた、メモ、料理の記録 |
| `items` | 元レシピID、料理名、量の倍率、基準の栄養と材料、表示量、アレルゲン、作り方など。任意で形態、商品の説明、買い物用の確認状況も保持 |
| `customRecipes` | 手入力から任意に保存する自分のメニュー |
| `pantry` | 材料IDと登録単位での手持ち数量 |
| `profile` | 年代、基準表の性別区分、活動量、比較方法 |
| `targets` | 手動で設定する6成分の比較値 |
| `completedDays` | その日の飲食をすべて記録したと利用者が確認した日付 |
| `shoppingChecks` | 購入済みの目印 |

`planned`は予定、`eaten`は食べた記録です。摂取量に使うのは`eaten`だけです。同じ日・区分に複数品を追加でき、食事回数は同じ日・区分を1食として数えます。

記録時点の料理名、栄養、材料を保存するため、元のDBを変えたり削除したりしても過去の内容を保持します。現在の料理名から店舗名を外しても、保存済みスナップショットの名前を自動で置き換えません。現行DBにない材料が記録へ残る場合も、その存在を消して買い物不要とは判断しません。

摂取量にはメニューごとの`quantity`を掛けます。`servings`は買い物用の人数です。4人分の料理を作っても、自分が1人分を食べた記録に4を重ねて掛けません。月表示は月曜始まりの42マスで、2000年から2100年までを扱います。

### 記録の範囲リセットとメニューからの登録

`record-actions.js`の`previewReset(state, filter)`は対象の`entryCount`・`itemCount`・`completedDayCount`を返します。`filter`は`{from, to, status, meals?}`で、範囲は両端を含みます。`status`は`all`・`planned`・`eaten`、省略した`meals`は4食すべてです。日数の上限は追加せず、既存の2000〜2100年の日付検査を使います。範囲に入る将来の予定も対象です。

`resetEntriesRange`は新しい状態を返して入力を変えません。対象外の記録、マイDB、設定、在庫などを保持します。予定だけを消す場合は完了チェックを保持し、実績を含む場合は範囲内の`completedDays`も取り消します。記録が0件の完了日も対象です。実行前の確認はUIで必須にし、件数と期間を表示します。直前の状態を1つだけ保持して取り消せるようにし、次のデータ更新や再読み込み後には持ち越しません。

`createCatalogEntry({recipeId, date, meal, status, amount, note}, data)`は、メニュー詳細から予定または実績を作ります。`describeRecipe`で情報を取得し、`recipePortion`と`quantityFromAmount`で表示単位を倍率に換算して`itemFromRecipe`へ渡します。未確認商品の記録も認めますが、確認フラグ、栄養の不明値、商品説明を変更しません。ここでアレルギー情報を確認済みにする処理は行いません。

## 栄養の値と不明分

対象はエネルギー、たんぱく質、脂質、炭水化物、食物繊維、食塩相当量の6成分です。材料の`nutritionPerUnit`は、その材料で宣言した1g・1ml・1個など当たりの値です。レシピの材料数量と基準人数から1人分を計算します。

材料の成分が不明なら、対応する料理の成分は`null`です。0と置き換えません。食事の合計では分かる値を足し、不明な成分があるかを別に管理します。食品成分表の対応、体積から重量への換算、概算の限界は[栄養値の出典](nutrition-sources.md)を参照してください。

最近の平均には`completedDays`の確認が済んだ日を使います。さらに栄養素ごとに不明分がある日を除き、分かる日数を分母にします。記録がない日を0として加えたり、入力途中の日から不足を断定したりしない構成です。1日の表示は入力途中でも確認できるようにし、平均の対象日数と区別します。

## 手作りの手順と購入品の情報を分ける

`data.js`の公開DBでは分類を整えた後に`decorateCookingInstructions(recipe, ingredients)`を適用します。既存ID、材料・分量、基準量、栄養の値を変更せず、手作りの現在の手順を補います。下ごしらえや切り方、加熱の順序、火の通りや仕上げの目安を料理に合わせて記述し、すべてを3工程へそろえません。新しい家庭用レシピは`varied-recipes.js`にも詳しい手順を持ちます。参照した料理の種類と家庭用にした範囲は[追加メニューの調査](menu-research-v3-4.md)へ記載します。

`instant`・`retort`・`fast-food`・`ready-to-eat`の組み込みメニューは、原材料から作る手順を付けず`steps: []`にします。画面では商品・食品の量と栄養の情報を中心にし、調理や再加熱は商品表示へ案内します。利用者が入力したマイメニューの手順は、この処理で削除・生成しません。保存済みの食事も現在のDBで手順を再生成せず、記録時点の内容を保ちます。

候補の検査では、手作りの手順欠落と、作り方が不要な購入品を区別します。手順がない手作りを正常なレシピとして戻すことはありません。購入品の手順が空でも、原材料とアレルギー情報の確認検査は省きません。商品名を指定した追加品は未確認フラグを持ち、栄養表示が分かるだけで自動提案へ入れないようにします。

`takeaway-foods.js`は商品名・規格・基準量・確認日と公式出典を持ちます。栄養は`manualNutrition`へ記録し、購入する商品を表す材料の栄養は全成分を不明にします。範囲表示や未掲載値を0へ補わず、計量単位に合わせて一度だけ換算します。詳細は[即席食品・惣菜・持ち帰り料理の出典](takeaway-food-sources.md)と[栄養値の出典](nutrition-sources.md)を参照してください。

### 料理名と栄養値の参照商品

公開DBのレシピの`name`・`variantLabel`、材料名、表示量の説明には店舗名を入れず、一般的な料理名と提供形態を使います。公式表示を使った場合は、実際に参照した店舗・商品名、味やサイズ、基準量、URLを`sourceNote`と出典文書へ残します。一般名へ変更しても栄養を一般的な代表値へ置き換えません。「出典の商品を参考にした記録例で、同じ料理でも量や栄養は異なる」という適用範囲を示します。店内単品を参照したものは「外食・単品」とし、持ち帰り商品へ読み替えません。

`confectionery-foods.js`と`dessert-foods.js`も商品の表示値と購入単位を保持します。参照商品の情報は[菓子・スナックの出典](confectionery-sources.md)と[スイーツの出典](dessert-sources.md)へまとめます。商品例は原材料やアレルギー情報の確認状況を明示し、栄養の出典があることだけで確認済みにはしません。

## 表記揺れに対応する検索

`japanese-search.js`の`normaliseJapaneseSearch`と`matchesJapaneseQuery`を共通に使います。NFKCで文字幅と互換文字をそろえ、英字の大小とカタカナを正規化し、収録料理・食材の漢字や別表記を辞書の共通形へ対応付けます。料理名の表示や保存済みの名前を変更する処理ではありません。未知の漢字を推測して読む機能は持たず、対応する表記は辞書へ追加します。

メニュー、記録のメニュー選択、優先・除外食材の検索で同じ照合を使います。料理名・小分類名の一致を材料だけの一致より先に表示し、同じ優先度では元の順序を保ちます。空白区切りはAND条件です。例えば「鶏肉 しょうが」なら両方を含む候補を探し、語順は問いません。水餃子と焼き餃子のような違いを残し、検索語を隣のフィールドへ連結して存在しない語を作りません。区分・形態・食材カテゴリなどの絞り込みや件数にも同じ検索条件を使います。

## プロフィールによる比較

18歳以上の年代、基準表の性別区分、活動量を利用者が選んだ場合に、`dietary-reference.js`から参考値を取得します。未選択を推測して埋めません。75歳以上の活動量「高い」など、原表に値がない組み合わせも自動補間しません。

エネルギーは参照体位に対する推定必要量、たんぱく質は推奨量、脂質と炭水化物はエネルギー比率の範囲を使います。脂質・炭水化物の中央のg値はアプリで比較しやすくするための換算値で、公式の推奨量とは分けます。食物繊維の「以上」と食塩相当量の「未満」も区別します。

手動の比較値も利用できます。妊娠・授乳中、18歳未満、体格による調整、治療用の自動設定は対象外です。基準は習慣的な食事を振り返る参考で、1日や少数の記録から健康状態を診断しません。根拠は[食事摂取基準の出典](dietary-reference-sources.md)にまとめています。

## 除外条件を先に確認する

献立作成と変更では同じ材料検査を通します。

1. レシピ、材料、分量、原料の参照を検査します。
2. 指定されたアレルゲンや個別食材を含む候補を除きます。
3. 残った料理を記録、好み、手持ちの食材から順位付けします。

`derivedFrom`は原料の材料IDです。トマト缶からトマトへたどることで、トマトの除外を缶にも適用します。アレルゲンも祖先から引き継ぎ、参照が不明・循環する候補を無視して戻しません。

食品群と主なたんぱく源は直接使う材料から求めます。しょうゆやみその原料が大豆であることだけで、大豆の主菜を1食食べたとは数えません。栄養そのものの量は材料の成分値から計算します。

ジャンルや気分は、除外条件を守れる候補の中での希望です。候補不足でもアレルギーや個別食材の除外を自動で取り消しません。市販品の配合と混入は登録DBだけでは判定できません。

`prepared-foods.js`の市販食品35品は`allergensKnown: false`、`ingredientsKnown: false`です。商品ごとの全原材料やアレルゲンを確認したデータではないため、記録や閲覧はできますが自動提案からは除外します。主食を固定した場合や差し替えでもこの条件を外しません。`recipeConfirmation`は即席・レトルト・ファストフードとマイメニューについて、確認フラグがない場合も確認済みとは扱いません。そのまま食べる市販サンドイッチのような一般例にも未確認フラグを明示します。

確認状況は性質から一律に決めず、食品ごとに保持します。単純な材料が分かる果物などは従来どおり扱い、実際の商品表示を確認したマイメニューは登録された材料とアレルゲンを再検査します。参考のアレルゲン一覧があることだけで商品全体を確認済みとは判断しません。

## 主食と飲み物を献立へ組み込む

`meal: all`は日付ごとに朝食・昼食・夕食を作ります。`days`は食数ではなく日数で、結果は日付と食事を組にした順序になります。カレンダーの各記録には`all`を保存せず、実際の食事区分を保存します。必要な候補が不足した場合は全体を未作成として返し、一部だけ予定へ登録しません。

主食はおまかせ、具体的な種類と量の固定、別の主食を追加しない設定を使います。内部は`stapleMode: adaptive | fixed`と`stapleId: auto | none | recipeId`を組み合わせます。おまかせでは食事区分や主菜に合わせた主食を各基準量で選びます。主食なしは別添えの主食を省く設定で、麺や丼の材料から米や麺を除く操作ではありません。

`updatePlanStaple`は生成後の1食だけを指定し、主食の追加・変更・削除と量を更新します。ほかの食事や全体の設定は保ち、栄養、予定のスナップショット、買い物へ同じ倍率を反映します。一品で主食を含む料理に別の主食を追加することや、除外条件に合わない主食への変更は認めません。飲み物も具体的な種類と量を指定できます。パスタやカレーライスなど一品で主食を含む料理は`mealBase`や分類から判定し、別の主菜やご飯を重ねない構成を使います。間食は間食メニューを中心に選びます。

ジャンル比率は希望する件数へ整数配分し、端数が大きいものから残りを割り当てます。希望ジャンルに候補がない場合は、除外条件に合う別ジャンルへ変更したことを知らせます。気分、優先食材、手持ちの食材も順位付けに使います。

### 順位付けと栄養の反映

`pick`は条件検査を通った候補から選びます。主菜で希望ジャンルに合う候補があればそこへ絞り、気分も合う候補がある範囲で使います。最近食べておらず今回の提案でも未使用の料理があれば優先し、候補が少ないときは重複を認めます。点数には料理の登場回数、優先食材、手持ちの食材、組み合わせに足りない食品群、主なたんぱく源の偏りなどを反映します。種に基づく値を同点付近の選択にも使うため、単純な栄養順や完全な無作為抽出ではありません。

栄養の順位付けは`calendarNutrientScore`で行います。対象はエネルギー、食塩相当量、たんぱく質、食物繊維の4成分です。エネルギーと食塩は過剰を抑える方向、たんぱく質と食物繊維は最近の平均が比較値より少ない場合に補う方向で点数を調整します。脂質と炭水化物は摂取量の集計と比較には使いますが、この順位計算には含めません。必要な記録や値がなければ、その成分による調整を省きます。不明値を0として優遇しません。

記録を使う提案は対象の食事より前の実食を参照します。最近の栄養には記録完了日の分かる成分を使い、当日の実食も対象の食事より前の分を扱います。未来の予定を摂取量へ含めません。今回生成した料理は提案内での重複調整に使い、食べた記録とは区別します。全成分の比較値へ厳密に一致させる最適化ではありません。

画面内の「献立はどうやって選ぶ？」はこの順序と制約を説明します。収録したテイクアウトや即席食品、市販の菓子・スイーツのうち未確認の商品例は自動提案から除きます。購入品という分類を一律に禁止する処理ではなく、確認状況と材料・アレルギーの検査で判断します。確認済みのマイメニューも同じ検査を通し、お酒は常に候補から除きます。

主食・飲み物の量は日ごとの`quantities`倍率にも保持し、献立の栄養、カレンダーへの保存、買い物で同じ倍率を使います。チェックを外した料理はその日の予定と買い物から除きます。

### 酒・プロテイン・補食の扱い

飲み物は清涼飲料水、プロテイン飲料、お酒、その他の飲み物を区別し、間食に補食・栄養補助食品を加えます。酒は飲んだ量を残す記録用で、`family: alcohol`は自動提案、固定飲み物、差し替えの候補から除きます。

商品例の`manualNutrition`は明示した基準量に対する公式表示の値です。[酒・飲料・補食の出典](performance-food-sources.md)に確認日と参照先を残します。原材料全体の登録とは別で、確認できない成分や範囲表示は`null`を残します。商品固有の栄養を参考配合から作り直しません。ソイとホエイ、粉末と調製済み飲料を区別し、水割りと牛乳割りは別レシピにします。粉末のgを液体のmlへ足して完成容量を推定せず、配合を1杯として記録します。牛乳割りでは牛乳の栄養とアレルゲンも加えます。

商品ラベルに基づく栄養が分かっていても、全原材料やアレルギー情報を確認済みとしません。`allergensKnown: false`・`ingredientsKnown: false`を保持し、自動提案には使いません。買う商品と量が分かることは`shoppingKnown`で別に扱います。

## 手入力と自分のDB

未登録の食事は名前と量だけでも記録できます。栄養の空欄は不明です。全材料を登録した場合に「材料から栄養の概算を入力する」を押すと入力欄を更新し、その後で商品表示の値などに修正できます。保存時に空欄を自動で計算しません。

材料全体とアレルギー情報の確認状況は別々に持ち、初期値は未確認です。アレルギー情報が未確認のメニューは自動提案せず、材料が未確認で追加除外食材がある場合も除きます。マイDBの保存は利用者が選びます。DB削除時も過去の記録は残し、削除した料理が選択中なら主食や飲み物の設定を戻します。

手入力では調理・提供形態と「栄養や商品のメモ」を任意で指定できます。`sourceNote`は商品表示や概算の前提を説明する文字列です。アレルギーの確認を代わりに済ませるものではありません。`shoppingKnown`は買う商品の種類と量がそろったという別の確認です。材料全体やアレルギーの確認とは独立して保存します。

## 必要量をまとめてから在庫を引く

買い物には提案中の献立かカレンダーの`planned`を使います。各材料にメニューの量と人数を掛け、同じ材料をすべて合計します。その後、在庫を食材ごとに一度だけ差し引きます。買う量は`max(0, 必要量 - 在庫)`です。

材料全体が未確認、または現行DBにない材料を含む場合は料理名を知らせます。空の材料一覧を買い物不要とは扱いません。購入済みチェックは目印で、数量在庫と区別します。在庫の消費は自動で行わず、利用者が使った分や買い足した分を更新します。

市販食品では原材料が未確認でも`shoppingKnown: true`で購入商品と量が登録済みなら集計できます。バーガーは完成品1個として数え、参考配合のバンズや肉を購入材料に展開しません。レトルトの完成1食は購入する具とご飯を集計します。この場合も原材料が未確認の料理として注意に残し、買い物を集計できることとアレルギー情報の確認を混同しません。`shoppingKnown: true`なのに商品一覧が空のデータは保存時に拒否します。

在庫の数量だけの変更では提案を維持して再集計します。除外条件や食べた記録など、候補選びの根拠を変えた場合は提案を作り直します。

## 保存形式と旧版からの移行

`localStorage`の`kondate-note-v3`に保存します。個人の記録やマイDBを送信する機能、自動同期はありません。提案は予定として登録するまで保存しません。

アプリと公開DBはv3.7.0ですが、保存形式とキーは引き続き`version: 3`・`kondate-note-v3`です。献立設定の`meal: all`を認め、`stapleMode`は任意の追加項目にします。旧v3で項目がない場合は主食IDから以前の指定を引き継ぎ、JSONへ必須項目を加えません。食材カテゴリと調理法も表示時に求めます。過去のスナップショットの量、栄養、確認状況は保持します。v3.1.0で追加した`nature`、`sourceNote`、`shoppingKnown`は引き続き任意項目です。追加項目のない旧v3のJSONも読み込み、数値や確認状況を後から作り直しません。形態は登録された列挙値、商品の説明は最大2000文字、確認状況は真偽値として検査します。

変更は複製した状態へ適用し、検査が成功してから現在の状態を置き換えます。JSONの型、許可する項目、日付、ID、数量、栄養、件数、2MBのサイズ制限などを検査し、危険なプロパティや重複ID、不正な参照を拒否します。不正ファイルで現在の記録を一部だけ書き換えません。

v1・v2からはアレルギー、除外条件、好み、食事の記録を引き継ぎます。v2の記録時点の栄養や材料も保ち、旧版にないプロフィールは未選択、記録完了日は未確認で始めます。読み込み時に旧キーや読み込めないデータを消しません。

メニューを増やすときは種類、主菜・副菜の食材カテゴリと調理法、調理・提供形態、基準量と完成状態、材料の単位、アレルゲンと原料、栄養の出典、調理手順をそろえます。階層だけを変える場合は既存のID・分量・栄養・保存形式を維持します。市販食品の参考配合と実商品の表示値は区別し、購入商品と原材料の確認状況を別々に定義します。人数や量を変えた計算、不明値、候補不足、旧版データも確認します。確認結果は[検証記録](validation.md)に残します。

`tools/sync_project.sh`はHTTPSで授業リポジトリへ同期する補助スクリプトです。main取得からコピー・コミット・pushを行うため、内容を確認して公開を意図した場合だけ実行します。個人のJSONを配布物へ混ぜません。公開はリポジトリ共通のGitHub Pages処理を使います。
