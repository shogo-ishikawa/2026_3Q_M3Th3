# 設計と開発

対応版：v2.0.0 ／ 更新日：2026年11月12日

## この版で扱うこと

献立ノートは食事カレンダーを中心に、食べた内容の振り返り、次の献立、買い物をつなぐアプリです。325品のメニューと160種類の食材・調味料を収録しています。ブラウザー内のJavaScriptで動き、アカウントや外部APIキーは使いません。

Pythonの学習には`meal_planner.ipynb`を使います。リスト・辞書・条件分岐・繰り返し・関数で候補を絞る仕組みを学ぶ教材です。カレンダー、栄養のグラフ、数量在庫などを含むブラウザー版の全機能は移植していません。`recipe_suggester.ipynb`は参考価格を扱う初期教材として残しています。

## 処理を分ける

| ファイル | 主な役割 |
| --- | --- |
| `data.js`・`expanded-foods.js` | メニュー、食材・調味料、アレルゲン、食品群の登録 |
| `ingredient-nutrients.js` | 食品成分表との対応、登録単位当たりの栄養値 |
| `planner.js` | 条件の確認、候補選び、記録を使った順位付け、組み合わせの変更 |
| `nutrition.js` | 1人分の栄養計算、量の倍率、期間集計、不明分の管理 |
| `journal.js` | カレンダーとマイDBの保存形式、入力検査、旧版からの移行、日付処理 |
| `shopping.js` | 予定の材料を合計し、手持ちの量を差し引く処理 |
| `app.js` | 操作、状態の更新、各機能の呼び出し、文字列としての安全な表示 |
| `storage.js` | 旧保存形式と従来APIの互換処理 |

## カレンダーは1人分を記録する

保存する状態は`version: 2`です。献立の設定、食事の記録、マイレシピ、手持ちの材料、栄養の比較値、買い物のチェックを持ちます。

| データ | 内容 |
| --- | --- |
| 食事の記録 `entries` | 識別子、日付、朝食・昼食・夕食・間食、予定／食べた、メモ、料理の一覧 |
| 料理の記録 `items` | 料理名、元レシピID、量の倍率、1人分の栄養と材料、食品群、アレルゲン、確認状況、作り方 |
| マイレシピ `customRecipes` | 手入力から任意に保存した1人分のメニュー |
| 手持ちの材料 `pantry` | 材料IDと、その材料の登録単位で測った数量 |
| 比較値 `targets` | 編集できる6成分の参考値 |
| 買い物のチェック `shoppingChecks` | 購入済みの目印。数量在庫は変えない |

`planned`はこれからの予定、`eaten`は実際に食べた記録です。栄養の摂取量に使うのは`eaten`だけです。同じ食事に複数の料理や記録を追加でき、食事回数の表示では同じ日付・区分を1食として数えます。

各料理は記録時点の内容を保存します。元のDBを変更・削除しても、過去の料理名や栄養が勝手に変わらないための仕組みです。過去のレシピIDや材料IDが現行DBになくても記録を保持し、買い物で材料を確認できない場合はその料理を知らせます。

カレンダーの基準は1人分です。`quantity`が0.5なら半分、2なら2人分相当として栄養を計算します。献立設定の`servings`は買い物用の人数です。4人分の料理を作る場合も、自分が標準の1人分を食べたなら摂取量へ4を掛けません。

日付は2000年から2100年までを扱います。月表示は月曜始まりの42マスです。範囲外になる端のマスは表示しても選択できません。

## 除外条件を先に確かめる

候補を選ぶ処理と組み合わせの変更は、同じ食材の検査を通します。

1. レシピと材料の情報、識別子、分量、原料の参照を確認します。
2. 指定したアレルゲンと個別食材を含む料理を除きます。
3. 残った候補を記録、好み、手持ちの食材などで順位付けします。

`derivedFrom`には原料の材料IDを登録します。例えばトマト缶からトマトへたどり、トマトの除外を缶にも適用します。先祖のアレルゲンも引き継ぎます。参照先が不明な場合や循環する場合は、問題を無視して候補へ戻しません。調味料も同じ検査の対象です。

食品群と主なたんぱく源は、直接使う材料から求めます。しょうゆやみその原料に大豆があっても、それだけで大豆の主菜を1食食べたとは数えません。バターの原料が牛乳であることだけで乳製品の食品群を追加することもありません。

候補が足りないときは不足する区分や指定メニューを知らせます。アレルギーや個別食材の除外条件を自動で外すことはありません。ジャンルや気分は、その条件を守った候補の中で使う希望です。

## 主食・飲み物・ジャンルを選ぶ

朝食・昼食・夕食では主菜・副菜・汁物を基本に、主食と飲み物を組み合わせます。間食では間食メニューを中心に選びます。主食はおまかせ、追加なし、具体的なメニューの指定に対応します。

丼や麺など、すでに主食を含む主菜には主食を重ねません。特定の主食を選んだ場合は、その主食と組み合わせられる主菜を使います。飲み物を含めて除外条件を確認し、指定が通らない場合は知らせます。

ジャンルはおまかせ、1種類の優先、割合の指定を使い分けます。割合は日数に合わせて整数件数に配分し、端数の大きいジャンルから残りを割り当てます。希望ジャンルに候補がないときは、除外条件に合う別ジャンルから選んだことを示します。

気分と優先食材、手持ちの食材も順位付けに使います。優先食材を必ず含める条件ではありません。生成後に料理のチェックを外すと、その日の予定保存と買い物の対象から外れます。

## 食べた記録から順位を調整する

カレンダー版の提案では対象日の6日前から、対象の食事より前までを参照します。同じ日の夕食を考える場合は朝食・昼食も使います。同じ食事や後の食事、未来の予定を摂取量に加えることはありません。

同じ料理や主なたんぱく源の繰り返しを減らし、分かる栄養の量も候補の優先順に使います。エネルギーと食塩相当量が比較値を超える方向への加点を避け、記録に少なかったたんぱく質や食物繊維を含む候補を選びやすくします。不明な成分を0として有利に扱いません。

記録していない食事は推定しません。食品群の登場回数は公式の食事バランスガイドの「つ（SV）」とは異なります。栄養も比較値を厳密に満たす最適化や個人の健康状態の判定には使いません。

## 栄養は概算と不明分を分ける

対象はエネルギー、たんぱく質、脂質、炭水化物、食物繊維、食塩相当量の6成分です。食材の`nutritionPerUnit`は宣言された1g、1ml、1個など当たりの値で、レシピの分量と基準人数から1人分を求めます。

材料の成分が不明なら、その料理の対応する成分は`null`のままにします。食事の合計は分かる値を足し、全料理の値がそろっているかを別の印で管理します。画面では「＋不明分」を添えるため、既知の合計を食事全体の確定量と誤解しにくくしています。

比較値は利用者が編集できます。初期値は学習用の参考値です。成分表との対応、体積の換算、調理による変化を再現しない範囲は[栄養値の出典と換算方法](nutrition-sources.md)を参照してください。

## 手入力のメニューを扱う

未登録の料理は名前と量だけでも記録できます。栄養や材料、作り方は分かる範囲で入力し、マイDBへの保存は利用者が選びます。栄養の空欄は不明のまま保存します。

「材料から栄養の概算を入力する」は、全材料を登録した確認を条件に入力欄を更新する明示的な操作です。保存時に空欄を自動で計算しません。商品の表示値が分かる場合は概算を入力した後に修正できます。

アレルギー情報と材料全体の確認状況は別々に持ち、初期値を未確認にします。アレルギー情報が未確認のメニューは自動提案しません。材料全体が未確認で追加の除外食材がある場合も候補から外します。全材料を確認したメニューは原料由来のアレルゲンと手動選択したアレルゲンを合わせて保持します。

マイDBを削除しても過去の記録は残します。削除した料理が選択中の主食や飲み物だった場合は設定を戻し、存在しない料理を選択した状態で保存しません。

## 買い物は必要量をまとめてから在庫を引く

買い物は提案中の献立か、カレンダーの予定を対象にします。指定期間の材料を、各料理の量と買い物用の人数を掛けてまとめます。カレンダーの`eaten`は対象にしません。

同じ材料の必要量をすべて合計してから、登録した手持ちの量を1回差し引きます。買う量は`max(0, 必要量 - 手持ち量)`です。複数日の料理ごとに同じ在庫を繰り返し引かない構成です。

全材料が未確認のメニューや、現行DBにない材料が含まれる場合は料理名を知らせます。空の材料一覧を買い物不要とは扱いません。購入済みチェックは目印であり、在庫の数量を変更するものではありません。

在庫の登録・数量変更・削除では提案中の献立を維持して買い物を再集計します。食材の除外条件や食べた記録など、提案の根拠が変わる操作では提案を作り直します。在庫の消費は自動記録せず、使った分や買い足した分を利用者が更新します。

## 保存と読み込み

記録は`localStorage`の`kondate-note-v2`へ保存します。個人の記録やマイDBをサーバーへ送る機能と端末間の自動同期はありません。作成途中の提案はカレンダーへ登録するまで保存しません。

状態の変更は複製したデータに適用し、検査が成功してから現在の状態を置き換えます。JSONの読み込みでも型、許可した項目、日付、識別子、数量、栄養、件数、2MBのサイズ制限などを確認します。重複ID、組み込みレシピと衝突するマイレシピ、危険なプロパティを拒否し、不正な入力で現在の記録を一部だけ変更しません。料理名やメモはHTMLとして挿入せず文字列で表示します。

旧`kondate-note-v1`と旧JSONはアレルギー、除外食材、好み、記録を引き継ぎます。記録は食べた状態の料理へ移し、メモだけの料理は栄養を不明として残します。旧キーや読み込めない保存データを読み込み時に消すことはありません。

JSONの書き出しには記録や設定も含まれます。一括で食事を削除する操作はカレンダーだけが対象です。マイDBや在庫、設定も消す場合はブラウザーでサイトの保存データを削除します。

## ローカルで開いて変更する

配布ZIPは`v2.0.0/`に展開します。Macでは例えば次の場所へ置けます。

```text
/Users/shogo/Dropbox/share_data/open_material/misc/apps/MealPlanner/v2.0.0
```

展開したフォルダーで起動します。表示されたURLをブラウザーで開き、終了はControl+Cです。

```bash
python3 tools/serve.py
```

主な確認と生成のコマンドは次のとおりです。Node.jsとPythonを使います。

```bash
npm test
python3 tools/build_notebook.py
python3 -m unittest discover -s tests -p 'test_*.py' -v
python3 tools/build_release.py
```

データを追加するときは材料ID、計量単位、アレルゲンと原料、栄養の出典、手順の対応を確認してください。人数や量を変えた計算、不明値、候補不足、過去の保存データも確かめます。実際の確認範囲は[検証記録](validation.md)に残します。

`tools/sync_project.sh`はHTTPSで授業リポジトリへ公開用ファイルを同期する補助スクリプトです。mainの取得、コピー、コミット、pushまで行うため、内容を確認して公開を意図した場合だけ実行してください。個人のJSONバックアップを配布物へ混ぜないでください。GitHub Pagesへの配信にはリポジトリ共通の公開処理を使います。
